# Travlr Getaways — Full Stack Web Application

**CS 465 Full Stack Development with MEAN**
Southern New Hampshire University

## Project Summary

Travlr Getaways is a full stack travel booking web application built on the MEAN stack — MongoDB, Express, Angular, and Node.js. The application serves two distinct audiences through two separate interfaces: a customer-facing multi-page website rendered server-side with Express and Handlebars, and an administrator single-page application (SPA) built with Angular that allows staff to manage travel packages with full CRUD functionality, protected by JWT authentication.

---

## Architecture

### Frontend Development Comparison

This project uses three distinct frontend development approaches, each suited to a different purpose:

**1. Express HTML with Handlebars (HBS) Templating**
The customer-facing website uses server-side rendering via Express and the Handlebars templating engine. When a user requests a page such as `/travel`, the Express server queries MongoDB, passes the trip data to a `.hbs` template, and renders a complete HTML page before sending it to the browser. This approach is ideal for the public-facing site because search engines can index the fully rendered HTML, page loads are fast for first-time visitors, and no JavaScript framework is required on the client side.

**2. Static JavaScript**
Earlier iterations of the project served static HTML pages enhanced with vanilla JavaScript. This approach is the simplest to deploy — no build step, no framework — but it scales poorly and lacks the separation of concerns that MVC architecture provides. Refactoring from static pages to HBS templates introduced a clean split between presentation logic (templates) and business logic (controllers).

**3. Angular Single-Page Application (SPA)**
The admin panel is built as an Angular SPA (`app_admin/`). Angular handles all routing client-side: when an administrator navigates between the trip list, add-trip form, and edit-trip form, the browser never does a full page reload. Angular components communicate with the Express REST API via `HttpClient`, and a JWT interceptor automatically attaches the authentication token to every outgoing request. The SPA approach is ideal for the admin tool because it provides a fast, app-like experience, clear component separation, strong TypeScript typing, and Angular's built-in reactive forms for data validation.

### Why MongoDB Over SQL?

MongoDB was chosen as the database for several reasons aligned with this project's requirements:

- **Schema flexibility**: Trip data is document-oriented — each trip is a self-contained JSON-like document. NoSQL document stores map naturally to this structure without the need for JOIN operations across multiple tables.
- **JSON throughout the stack**: MongoDB stores BSON (Binary JSON), the REST API exchanges JSON, and Angular consumes JSON. There is no translation layer required between the database and the client — the same data shape flows all the way through.
- **Rapid iteration**: During development, adding new fields to a trip (e.g., `perPerson`, `image`) required only a Mongoose schema update, not a database migration. This flexibility is valuable in early-stage development.
- **Node.js ecosystem fit**: The Mongoose ODM integrates natively with Node.js, providing schema validation, middleware hooks, and a promise-based query API that pairs well with `async/await`.

## Functionality

### JSON and the Full Stack Connection

JSON (JavaScript Object Notation) is a lightweight data-interchange format, but it is distinct from JavaScript itself. JSON is a text-based serialization format — it can be parsed and generated by any language. JavaScript objects, by contrast, are live in-memory data structures with methods and prototypes. The key differences are:

- JSON keys must be quoted strings; JavaScript object keys may be unquoted.
- JSON values are limited to strings, numbers, booleans, arrays, objects, and `null`. JavaScript objects can hold functions, `undefined`, and circular references.
- JSON cannot represent `Date` objects directly (they serialize as strings).

In this project, JSON acts as the universal contract between every layer of the stack:

1. **MongoDB → Express**: Mongoose retrieves trip documents and serializes them to JavaScript objects.
2. **Express → Angular**: The REST API responds with `res.json(trips)`, converting those objects to JSON text over HTTP.
3. **Angular → UI**: `HttpClient` deserializes the JSON response back into TypeScript objects, which Angular binds directly to the template.
4. **Angular → Express (writes)**: When an admin submits a form, Angular serializes the `FormGroup` value to JSON and POSTs it to the API, which Mongoose then writes back to MongoDB.

This clean JSON pipeline is what makes the MEAN stack uniquely cohesive: the same data format is native to every component.

### Code Refactoring Examples

Several significant refactors were performed throughout the project:

**1. Static HTML → MVC with HBS**
The initial site served raw HTML files from `public/`. Refactoring to Express MVC moved all route logic into `app_server/routes/index.js` and `app_server/controllers/travlr.js`, replaced static HTML with Handlebars templates sharing a common `header.hbs` and `footer.hbs` partial, and made the trip data dynamic. This eliminated duplicated markup across seven pages and made the layout maintainable from a single location.

**2. Hardcoded data → MongoDB**
The travel page originally iterated over a static `trips.json` file embedded in the controller. Refactoring wired the controller to Mongoose (`Trip.find()`) so that the page reflects live database state. The JSON file was retained as a seed source and fallback, but the authoritative data source became MongoDB.

**3. Monolithic API routes → Separation of Concerns**
Initially, route handlers contained inline database logic. Refactoring moved all database operations into `app_api/controllers/trips.js`, leaving `app_api/routes/index.js` responsible only for routing decisions and middleware application (including the `jwtAuth` guard). This made each function independently testable and the route file readable at a glance.

**4. Unprotected API → JWT Middleware**
Adding authentication required minimal changes to existing trip routes: a single `jwtAuth` middleware function was inserted before `tripsAddTrip`, `tripsUpdateTrip`, and `tripsDeleteTrip`. The `GET` endpoints remain public so the customer-facing site can read trips without a token. This surgical change demonstrates the value of the controller/route separation established in the prior refactor.

## Testing

### API Endpoint Testing

Functional testing of the REST API was performed using **Postman** at each development stage:

| Method | Endpoint | Auth Required | Expected Status |
|--------|----------|---------------|-----------------|
| GET | `/api/trips` | No | 200 |
| GET | `/api/trips/:tripCode` | No | 200 |
| POST | `/api/register` | No | 200 + token |
| POST | `/api/login` | No | 200 + token |
| POST | `/api/trips` | Yes (Bearer JWT) | 201 |
| PUT | `/api/trips/:tripCode` | Yes (Bearer JWT) | 200 |
| DELETE | `/api/trips/:tripCode` | Yes (Bearer JWT) | 200 |

**Testing procedure for authentication:**
1. `POST /api/register` with `{ "email": "admin@travlr.com", "password": "test1234" }` → copy the returned token.
2. `POST /api/login` with the same credentials → confirm a fresh token is returned.
3. `PUT /api/trips/BEACH001` **without** an `Authorization` header → confirm `401 Unauthorized`.
4. Repeat the same PUT **with** `Authorization: Bearer <token>` → confirm `200 OK` and updated document returned.

**Challenges:**
The primary testing challenge was the `passport-local-mongoose` ESM/CommonJS interop issue — the package exports its plugin as a `.default` property in newer versions, which caused a runtime error when accessed via `require()`. Debugging this required inspecting the module's export shape with `node -e "console.log(typeof require('passport-local-mongoose'))"` before identifying the fix (`require('passport-local-mongoose').default`).

Security affected testing by adding a required pre-condition to any write test: a valid JWT must first be obtained. Postman environments were used to store the token value as a variable and automatically inject it into subsequent requests, simulating the behavior of the Angular JWT interceptor.

## Security

A single layer of JWT security was applied to the SPA admin side:

- **User model** (`app_api/models/user.js`): Mongoose schema with `passport-local-mongoose` plugin, which handles password hashing with `pbkdf2` (salted, iterated) — passwords are never stored in plaintext.
- **Registration/Login** (`app_api/controllers/authentication.js`): On successful authentication, `jsonwebtoken` signs a payload containing the user's email with a server-side secret and an expiry of one hour.
- **JWT Middleware** (`jwtAuth` in `app_api/routes/index.js`): All write-capable endpoints verify the token on every request. An invalid or missing token returns `401 Unauthorized` immediately, before any database logic executes.
- **Angular Auth Guard** (`app_admin/src/app/utils/auth.guard.ts`): Prevents navigation to protected routes client-side, redirecting unauthenticated users to the login page.
- **JWT Interceptor** (`app_admin/src/app/utils/jwt.interceptor.ts`): Automatically attaches the `Authorization: Bearer` header to every outgoing HTTP request, so no individual service call needs to manage the token.

## How to Run the Application

### Prerequisites
- Node.js v18+
- MongoDB running on `localhost:27017`
- Angular CLI (`npm install -g @angular/cli`)

### Backend (Express server)
```bash
# From project root
npm install
npm run seed          # seed the database with initial trip data
npm start             # starts on http://localhost:3000
```

### Frontend (Angular SPA admin)
```bash
cd app_admin
npm install
ng serve              # starts on http://localhost:4200
```

### First-time admin setup
1. With the Express server running, use Postman (or curl) to create the first admin user:
   ```
   POST http://localhost:3000/api/register
   Body: { "email": "admin@travlr.com", "password": "yourpassword" }
   ```
2. Navigate to `http://localhost:4200` and log in with those credentials.

## Reflection

### Professional Growth

This course challenged me to think across the entire software stack simultaneously. Working with Express, I had to understand both the server's routing responsibilities and the template rendering pipeline. Working with MongoDB and Mongoose, I learned how schema design decisions — even in a "schema-less" database — significantly impact query performance and data integrity. Building the Angular SPA required me to internalize a component-driven architecture, reactive programming with RxJS Observables, and the Angular dependency injection system.

The most transferable skill developed in this course is the ability to reason about data contracts between system boundaries. Every handoff — controller to template, API to client, database to API — requires a clearly defined interface. Disciplined attention to those interfaces (modeled here by the JSON schema of the Trip object) is what makes a full stack system maintainable as it grows.

The addition of JWT authentication reinforced a principle applicable to every professional security context: defense in depth means securing both the client (route guards, hidden UI elements) and the server (JWT middleware on every write endpoint). Client-side security is a usability feature; server-side security is the actual protection.

### Skills Developed
- **MEAN stack integration**: end-to-end development from database schema to browser UI
- **RESTful API design**: HTTP method semantics, status codes, and stateless authentication
- **Angular**: components, services, reactive forms, routing, HTTP interceptors, route guards
- **MongoDB/Mongoose**: schema modeling, seeding, async queries with `async/await`
- **JWT authentication**: token generation, verification middleware, secure storage patterns
- **Debugging across the stack**: reading Node.js stack traces, browser network inspector, Postman testing
